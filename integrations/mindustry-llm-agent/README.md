# Mindustry 단일 LLM 기준선

이 저장소는 캡스톤 프로젝트의 1차 실험인 `LLM → 게임 상태 → 판단 → 명령 → 행동` 루프를 구현합니다. 현재 기준 모델은 Ollama의 `deepseek-v4.1-flash:cloud`이며, Mindustry v159.7 headless 서버 플러그인이 게임 상태와 행동 API를 제공합니다.

## 현재 구현 범위

- 상태: 맵/웨이브/tick, 코어 크기·점유 타일·체력·자원, 건물의 재고·효율·생산물, 아군·적 유닛 타일 좌표, 적 스폰, 주변 광물
- 게임 지식: 허용 블록의 건설비·용도·입력 소비량·출력 레시피·제작 시간·저장 용량·전력 소비/생산량·포탑별 표적·사거리·연사력·탄약별 피해/DPS/특수 효과·유닛 생산 계획을 Mindustry v159.7 콘텐츠 정의에서 동적으로 제공
- 포탑 입력 압축: 건설 가능·기보유·관측된 자원원으로 도달 가능한 포탑만 상세 전투 수치를 전달하고, 나머지는 이름·비용·부족 자원을 `deferred_turrets`에 보존
- 행동 폭: 요청 안정성을 위한 턴당 32행동은 유지하되, LLM이 큰 투자를 선택할 수 있도록 매크로 구리 예산은 5000, 방어 매크로 포탑 수는 8까지 허용
- 생산망 진단: 건물별 `noInput`/`noOutput`/비활성 상태, 입력별 보유량과 충족 여부, 제작 진행률, 출력 대상·인접 건물, 액체 재고, 전력망 ID·수요·공급·충족률을 제공
- 물류망 진단: 연결 컴포넌트별 범위·생산원·최종 소비처·열린 출력·순환 여부와 선택적 소비처별 자원 도달성, 최초 관측 단절 좌표, 잘못 향한 인접 벨트를 제공
- 전략 작업 기억: LLM이 직접 작성한 현재 능력·제약·기회·불확실성과 장기 의도를 다음 판단에 다시 전달하여, 매 턴 단기 대응으로 초기화되지 않도록 함
- 유지보수 관측: 파괴 건물은 재건·대체·재설계·포기 중 하나를 LLM이 선택할 때까지 사실 백로그에 유지하고, 손상 건물은 체력 비율과 좌표를 별도 요약
- 에피소드 격리: JSONL 로그는 평가·분석 기록으로만 남기며, 과거 로그를 회고 메모리로 변환하거나 다음 실행의 판단 입력에 넣지 않음
- 좌표 지원: 드릴 후보마다 실제 생산 자원과 포함 광맥 수를 제공하고, 드릴·컨베이어·Duo·구리 벽의 서버 검증 배치 좌표 제공
- 행동: 현재 게임에서 실제로 건설 가능한 블록의 직접 `place`, `remove`, LLM이 드릴·운송 수단·목표 건물을 고르는 채굴망, 범용 아이템/액체 경로, 전력 연결, 유닛 공장 계획 선택(최대 32개/턴)
- 방어 선택: 서버가 좌표를 고르는 방어 매크로는 비활성화되어 있으며, LLM이 진입로별 배치 후보를 비교한 뒤 포탑·벽의 정확한 좌표를 `place`로 직접 선택
- 규칙: 실제 배치 가능 여부와 금지 블록을 검사하고 코어 자원을 차감
- 안전성: 관측한 `episode_id`와 실행 시점의 에피소드가 다르면 HTTP 409로 요청 전체 거부
- 빠른 전투 반응: 코어 기체와 같은 등급의 에이전트 수비 기체 1대가 코어 주변에서 자동 조준·사격
- LLM 주도 방어 보급: 각 포탑의 원시 탄약 충전률과 호환 탄약을 관측하고, 모델이 `resupply_turrets`를 선택할 때만 코어 자원을 이전
- 전투 관측: 코어 체력 비율, 최근접 적 거리와 12/20/30타일 내 적 수를 제공하되 위험 등급은 코드가 판정하지 않음
- 코어 유닛 활용: 베타의 현재 임무·위치·체력·사거리·적재량·채굴/건설 능력뿐 아니라 임무 경과 시간, 현재 단계, 누적 배송량을 관측하고 모델이 `idle`, `mine`, `supply`, `defend_core`, `intercept`, `repair`, `rebuild` 임무를 직접 지정
- 기록: 매 턴 상태, 모델 판단 요약, 행동별 성공/실패, LLM 지연·토큰 사용량을 JSONL로 저장

현재 행동 어댑터는 전략 실험을 빠르게 시작하기 위해 건설 시간을 생략하고 완성된 건물을 즉시 놓습니다. 자원 비용과 배치 규칙은 지킵니다. 이후 LLM과 군집 에이전트 모두 같은 어댑터를 사용해야 비교가 공정합니다.

LLM의 고정 게임 지식에는 웨이브 보상/적 구리 드롭이 없다는 경제 규칙, 코어 구리 비축선,
드릴 점유 타일과 생산 자원, 컨베이어 방향, 포탑 탄약, 벽·전력·공장의 역할이 포함됩니다.
블록별 수치와 생산 레시피는 프롬프트에 하드코딩하지 않고 실행 중인 Mindustry 콘텐츠 정의에서
읽습니다. 따라서 전략은 LLM이 세우되, 그 판단에 필요한 게임 규칙과 현재 가동 불능 원인은
서버 권위 상태로 전달됩니다.
최근 실패에는 원래 시도한 행동도 함께 전달되어 같은 실패를 좌표만 잊은 채 반복하지 않습니다.

## 구조

```text
Mindustry v159.7 headless server
  └─ Java bridge plugin (127.0.0.1:8765)
       ├─ GET  /v1/state
       └─ POST /v1/action
                 ↑
Python single-agent loop
  └─ Ollama OpenAI-compatible API
       └─ deepseek-v4.1-flash:cloud
```

LLM은 건설·자원·방어 배치를 정하는 전략 계층입니다. 서버의 자동 코어 수비기는
게임 틱마다 가까운 적을 조준·사격하는 반응 계층입니다. 긴급 전투를 클라우드 왕복에
맡기지 않으며, 이후 LLM과 군집 에이전트 비교에서도 같은 반응 계층을 사용합니다.

## 학습 및 적응 구조

전략은 웨이브별 건물 수나 체력 임계값으로 하드코딩하지 않습니다. Java 어댑터는 게임의
원시 사실과 실행 가능한 행동만 제공하고 Python 계층은 연속 관측의 차이를 사실 사건으로
변환합니다.

```text
게임 원시 상태
  → 사건 추출(건물 추가/파괴/피해, 코어 피해, 탄약 소비, 자원 변화, 웨이브 변화)
  → 현재 LLM 판단(현재 상태 + 이번 에피소드의 최근 사건 + 행동 결과)
  → 서버 검증 행동
```

사건 추출은 “무엇이 변했는가”만 계산합니다. 파괴된 Duo를 같은 위치에 복구할지, 다른
포탑으로 대체할지, 벽을 추가할지, 해당 전선을 포기할지는 LLM이 결정합니다. 에피소드
과거 실행의 회고나 교훈은 전달하지 않습니다. 특정 자원 순서·웨이브 임계값·발전 단계는 코드가 지정하지 않습니다.
LLM은 건물 카탈로그와 현재 생산망에서 인과관계를 해석하고, 자신의 전략 의도와 완료 근거,
수정 조건을 작성해 다음 턴에 이어갑니다.

## 준비물

- Windows + JDK 17 (Mindustry 공식 빌드 요구사항)
- Python 3.10 이상(외부 Python 패키지 없음)
- Ollama가 실행 중이고 `deepseek-v4.1-flash:cloud`가 연결된 상태

주의: `deepseek-v4.1-flash:cloud`를 사용하면 구조화된 게임 상태와 프롬프트가 Ollama의 클라우드 서비스로 전송됩니다. 민감한 데이터는 상태나 프롬프트에 넣지 마세요.

## 실행

PowerShell 1에서 서버를 준비하고 실행합니다.

```powershell
.\scripts\setup-server.ps1
.\scripts\run-server.ps1
```

서버 콘솔이 뜨면 고정 맵으로 시작합니다.

```text
host Fork survival
```

PowerShell 2에서 먼저 행동 없는 검증을 합니다.

```powershell
.\scripts\run-agent.ps1 -DryRun -MaxTurns 1
```

정상이라면 실제 기준선을 실행합니다.

```powershell
.\scripts\run-agent.ps1 -Model deepseek-v4.1-flash:cloud -ReasoningEffort none -MaxTurns 20
```

### 게임 화면으로 관전하기

서버에서 `host Fork survival`을 실행한 뒤 그래픽 클라이언트를 엽니다.

```powershell
.\scripts\setup-client.ps1
.\scripts\run-client.ps1
```

Mindustry 창에서 `플레이 → 멀티플레이 참가 → 서버 추가`를 선택하고
`127.0.0.1:6567`에 접속합니다. 게임 화면이 보이면 다른 PowerShell 창에서
`run-agent.ps1`을 실행합니다. 에이전트가 배치한 드릴, 컨베이어, 포탑이
접속한 클라이언트 화면에 실시간으로 동기화됩니다.

게임 채팅에서도 LLM 에이전트를 제어할 수 있습니다. 채팅창은 기본적으로
Enter 키로 엽니다.

```text
/agent-start       # 기본 20턴 시작
/agent-start 5     # 5턴만 시작
/agent-status      # 실행 상태 확인
/agent-stop        # 진행 중인 LLM 호출과 행동 중단
/game-restart      # 에이전트 중단 후 Fork survival을 새 에피소드로 초기화
```

`/game-restart`는 서버를 잠시 닫고 같은 Fork 맵을 다시 호스트하므로 클라이언트가
연결 해제되면 `127.0.0.1:6567`로 재접속해야 합니다. 재접속 후 `/agent-start 500`을 실행하면
새 에피소드의 현재 상태만으로 판단을 시작합니다.

안전을 위해 로컬 접속자 또는 서버 관리자만 시작·중단할 수 있습니다. GUI 버튼은
클라이언트 모드를 별도로 설치해야 하므로, 현재 버전은 추가 설치가 필요 없는 게임
채팅 명령을 사용합니다.

로그는 `runs/*.jsonl`에 생성됩니다. 한 실행의 요약은 다음처럼 봅니다.

```powershell
python -m mindustry_agent.report runs\실행파일.jsonl
```

## GLM-5.3-Flash 대 DeepSeek 실시간 PvP

PvP 프롬프트는 웨이브 디펜스 프롬프트와 별도로 선택되며, 상대 코어 파괴와 경제→생산→유닛
운용→공격의 인과관계를 경기 목표로 둡니다. 공통 게임 규칙과 행동 형식만 공유합니다. PvP에
참가하는 두 모델끼리는 완전히 같은 PvP 프롬프트, 상태 스키마, 행동 API를 사용합니다. 각 모델은
자기 팀을 기준으로 상태를 받고 독립적으로 판단하며, 먼저 도착한 응답부터 즉시 해당 팀에
적용됩니다. 따라서 모델 응답 지연도 경기 성능에 포함됩니다. 팀 이름 자체는 전략 힌트로
쓰이지 않으며, 서버가 사람 없는 PvP 경기를 자동으로 멈추지 않도록 설정됩니다.

PowerShell 1에서 PvP 서버를 실행합니다.

```powershell
.\scripts\run-pvp-server.ps1
```

서버 콘솔이 준비되면 팀당 코어 하나인 기본 경기장을 엽니다.

```text
pvp-start
```

화면으로 보려면 별도 PowerShell에서 `.\scripts\run-client.ps1`을 실행하고
`127.0.0.1:6567`에 접속합니다. 이어서 PowerShell 2에서 두 에이전트를 동시에 시작합니다.

```powershell
.\scripts\run-pvp-agents.ps1 -MaxTurns 500
```

브리지를 다른 포트로 띄운 검증 환경에서는 `-ApiUrl http://127.0.0.1:8877`처럼 명시할 수
있습니다. 이 값은 사전 상태 확인뿐 아니라 실제 두 Python 에이전트에도 동일하게 전달됩니다.

또는 게임 채팅창을 열고 아래 명령 하나만 입력해 두 에이전트의 실제 행동을 시작할 수 있습니다.

```text
/agent-start 500
```

RTS 모드에 로컬 클라이언트로 접속하면 자동으로 완전한 중립 관전자로 전환됩니다. 자동 전환되지
않았거나 다시 관전 모드로 들어가려면 게임 채팅에 다음을 입력합니다.

```text
/spectate
```

플레이어 유닛이 제거되고 `derelict` 중립 팀으로 이동하며 카메라는 맵 중앙으로 이동합니다. 마우스 휠로
축소하고 드래그 또는 WASD로 자유롭게 이동할 수 있습니다. 다음 맵으로 넘어가도 관전자 상태가 유지됩니다.
팀으로 돌아가려면 `/spectate-off sharded` 또는 `/spectate-off crux`를 사용합니다.

현재 게임이 PvP이면 `/agent-start`가 자동으로 GLM-5.3-Flash와 DeepSeek 양쪽을 동시에 실행합니다.
명시적인 `/pvp-agent-start 500`도 같은 동작을 하며, `/agent-status`, `/agent-stop`으로
두 프로세스의 상태 확인과 중단이 가능합니다. 로컬 접속자 또는 서버 관리자만 실행할 수 있습니다.

`Glacier`는 각 팀의 코어 위치를 불러오는 용도로만 사용합니다. `pvp-start` 직후 코어 이외의
장애물과 기존 건물을 제거하고 돌 평지로 바꾸므로 이동 경로상의 지형 차이가 없습니다. 기본
배정은 GLM-5.3-Flash=`sharded`, DeepSeek=`crux`이며 모델은 각각 `glm-5.3-flash:cloud`,
`deepseek-v4.1-flash:cloud`입니다. GLM-5.3-Flash는 지원되는 빠른 설정인 `low`, DeepSeek는 `none`으로
실행하며, 두 모델의 실제 응답 지연은 각 턴 로그에 그대로 기록됩니다.

`pvp-start`는 구리·납·석탄·모래·티타늄·토륨 패치를 한쪽에 만든 뒤 두 코어 중점을 기준으로
반대편에 점대칭 배치합니다. 따라서 각 자원의 광맥 타일 수, 코어 기준 상대 위치, 드릴 배치
기회가 동일합니다. 적용 결과는 상태의 `pvp_fairness`에 평탄화 타일 수, 자원별 타일 수,
지형·자원 대칭 불일치 개수로 기록됩니다. Mindustry 광맥은 고갈되지 않으므로 별도의 유한
매장량 대신 동일한 광맥 타일 수가 동일한 채굴 기회를 보장합니다.

### 자원 비축형 RTS PvP

채굴과 벨트 설계 영향을 제외하고 공장 투자, 유닛 조합, 병력 집중·분산, 정찰, 공격과
후퇴 전략을 비교하려면 별도 RTS 모드를 사용합니다. 기존 `pvp-start`는 변경되지 않습니다.

```powershell
.\scripts\run-rts-server.ps1
```

서버 콘솔이 준비되면 다음 명령으로 RTS 경기장을 만듭니다.

```text
rts-start
```

`rts-start`는 두 코어 이외의 맵을 평지로 만들고 모든 광맥을 제거한 뒤, 양 팀 코어에
게임의 모든 비숨김 자원을 종류별로 12,000씩 동일하게 지급합니다. 구리·납뿐 아니라
베릴륨·텅스텐·산화물·카바이드 등 상위 공장과 유닛에 필요한 자원도 포함됩니다. 공장 건설비와
유닛 생산비는 표시된 정규 비용대로 차감되지만, 시연 중 일반적인 생산·강화·방어 선택이 자원
부족 때문에 막히지 않을 만큼 충분하며 양 팀에 완전히 동일하게 적용됩니다.

### 전략형 3개 전선 시연 맵

공정성 측정용 평지 `rts-start`를 유지하면서, 관전 시 전략 차이를 더 뚜렷하게 보려면 서버나
게임 채팅에서 다음 명령을 사용합니다.

```text
showcase-rts-start
```

이 모드는 동일한 비축량·건설·생산·점령 규칙을 사용하지만 전장 중앙에 점대칭 중립 암벽을
배치해 북부·중앙·남부의 세 지상 통로를 만듭니다. 각 통로에는 시각적으로 구분되는 바닥,
점대칭 집결 공간, 엇갈린 사격선과 거점 주변 엄폐물이 있으며 거점 중심은 이동 가능하게
열려 있습니다. 각 통로의 점령 거점은 생산·업그레이드 속도와 전방 회복 이점을 제공하므로 한곳
집중, 병력 분할, 측면 우회, 전선 간 회전, 요충지 방어와 코어 공략 사이에 실제 기회비용이 생깁니다.
공중 유닛은 중립 암벽을 무시하므로 지상군 병목을 우회할 수 있습니다.

유일한 승리 조건은 상대 코어 파괴입니다. 거점은 직접 승리를 제공하거나 자원을 지급하지 않습니다.
대신 소유한 거점마다 유닛 생산·업그레이드 속도가 10%씩 빨라져 최대 30%까지 중첩되며, 경합 중이
아닌 소유 거점 범위 안의 아군 전투 유닛은 초당 최대 체력의 1%를 회복합니다. 소유 중인 거점도
적이 진입해 경합 상태가 되면 두 이점이 모두 잠시 중단됩니다. 점령 병력 추가에 따른 점령 속도는
최대 1.5배까지만 증가합니다. 현재 거점 소유권, 실제 효과가 활성화된 거점 수, 양 팀의 속도 배율과
회복 효과는 매 판단마다 양쪽 모델에 동일하게 전달됩니다. RTS 서버는
사망 유닛을 클라이언트까지 `unitDestroy`로 즉시 동기화하므로
비행 유닛의 낙하 잔해나 유령 스프라이트가 살아 있는 유닛의 이동·표적 선택·관전을 방해하지 않습니다.

모델에는 `rts_battlefield`로 각 통로 ID, 정확한 통과 좌표 범위, 지상 경로 특성, 공중 접근성만
동일하게 전달됩니다. 실행기는 선호 통로, 병력 비율, 점령 순서 또는 고정 빌드 순서를 정하지
않습니다. 중립 암벽은 양측에 완전히 대칭이며 파괴할 수 없는 지형이므로 어느 진영도 지형상
우위를 갖지 않습니다.

`place`는 즉시 완성되지 않습니다. 양 팀은 각각 하나의 동일한 순차 건설 대기열을 사용하며,
건설비는 명령 시 예약되고 건물별 정규 건설 시간이 지난 뒤 완성됩니다. 한 응답에 여러 건물을
선택하는 것은 모델이 정한 건설 순서가 될 뿐 동시 즉시 건설은 아닙니다. 대기 중인 위치와 남은
시간은 `rts_construction_queue`로 전달됩니다. 이는 공장 종류나 수량을 정하는 전략 규칙이 아니라
두 모델에 동일하게 적용되는 실행 속도입니다.

이 모드의 유닛 공장은 생산 슬롯입니다. 모델이 공장을 배치한 뒤 `train_units`로 공장,
유닛 종류와 수량을 선택하면 해당 유닛 계획의 정규 자원 비용을 즉시 지불하고 정규 생산
시간마다 한 대씩 생성합니다. 벨트와 전력은 RTS 생산에 필요하지 않으며, 공장 하나에는
동시에 하나의 생산 대기열만 존재합니다. 여러 공장을 지으면 병렬 생산할 수 있습니다.
`train_units`에 선택적으로 집결 좌표와 `squad_id`를 함께 지정하면 생산 완료된 유닛이 해당 위치로
이동해 같은 지속 분대에 자동 편입됩니다. 분대 상태에는 남은 생산 수, 생산·집결 완료 여부와
`producing → assembling → ready → advancing/engaging` 수행 단계가 전달됩니다. 언제 출발하고 어디를
공격할지는 실행기가 정하지 않으며, 모델이 새 관측을 보고 `command_units`로 결정합니다.
재구성기도 별도 생산 슬롯으로 취급합니다. 모델이 상태에 표시된 정확한 `기본 유닛 → 상위 유닛`
쌍을 선택해 `upgrade_units`를 호출하면, 정규 재구성 비용과 시간이 적용되고 입력 유닛은 강화
대기열에 들어갑니다. RTS 모드에서는 벨트·페이로드 컨베이어·액체·전력 연결 없이 작동하며,
각 재구성기에는 동시에 하나의 강화 대기열만 존재합니다. 상태에는 기본·상위 유닛의 체력, 방어력,
속도, 사거리, 추정 DPS, 지상/공중 공격 가능 여부, 이동 방식과 무기 정보가 함께 전달됩니다.
따라서 특정 유닛이나 강화 순서를 코드로 고정하지 않고 모델이 상대 조합과 비용을 비교합니다.

방어도 같은 전략 선택지로 열려 있습니다. RTS 상태의 `rts_defense`에는 현재 사용할 수 있는
아이템 탄약식 포탑과 벽의 건설비·건설 시간·체력·크기, 포탑의 사거리·대공/대지 여부·발사율과
탄약별 피해량이 전달됩니다. 적 코어에서 아군 코어로 이어지는 현재 접근 경로마다 실제로 유효한
포탑 좌표와 경로 인근 벽 좌표도 추천 순위 없이 제공됩니다. 포탑과 벽 역시 공장과 동일한 순차
건설 대기열을 사용하므로 방어 투자는 생산 시점을 늦추는 실제 선택입니다. 아이템 포탑은 자동
보급되지 않으며, 모델이 `resupply_turrets`를 명시적으로 선택할 때만 코어의 유한 탄약이 벨트 없이
전달됩니다. 어떤 포탑이나 벽을 언제 몇 개 지을지는 코드에서 정하지 않고, 모델이 상대 병력·경로·
남은 자원·건설 대기열·기존 포탑 탄약 상태를 비교해 판단합니다.

각 팀은 전용 RTS 프롬프트와 `rts_construction_queue`, `rts_training_queues`,
`rts_upgrade_queues` 상태를 동일하게 받습니다. 모델이 반환한 `wait_seconds`와 관계없이 RTS에서는
응답과 행동 처리 0.5초 뒤 새 상태를 전달합니다. 모델 응답에 걸린 실제 시간 자체는 경기 시간에
포함됩니다.
공장과 재구성기 배치 후보는
코어 인접 좌표에 한정하지 않고 반경 64타일 안의 4개 거리대와 8개 방향에서 현재 유효한
좌표를 분산 추출합니다. 후보 순서는 경기별로 동일하게 섞이며 추천 순위가 아니므로, 모델이
이동 거리·노출·밀집도와 상대 위치를 보고 가까운 생산 시설, 분산 시설 또는 전진 시설을 선택합니다.
각 후보에는 `placement_option_id`가, 완성된 공장과 재구성기에는 `facility_id`가 함께 전달됩니다.
모델은 좌표를 다시 작성하는 대신 이 ID를 선택할 수 있으며, 실행기는 최신 관측에서 ID의 유효성과
선택한 블록·시설 종류의 호환성만 검증합니다. 어떤 시설·유닛·수량을 선택할지는 여전히 모델의 전략입니다.

클라이언트로 `127.0.0.1:6567`에 다시 접속한 뒤 게임 채팅에서 시작합니다.

```text
/agent-start 500
```

```powershell
.\scripts\stop-pvp-agents.ps1
```

각 모델 로그에는 관측 시점 `observed_tick`, 행동 적용 시점 `action_applied_tick`, LLM 지연,
행동 결과가 따로 기록되어 승패뿐 아니라 응답 속도와 실행 성공률도 비교할 수 있습니다.
에이전트의 첫 판단이 도착한 뒤에는 게임 화면 상단 HUD에 양 팀의 실제 모델명, 코어 체력,
현재 유닛 수, 판단 번호, 최근·평균 모델 응답 시간, 실행 행동 수와 모델이 밝힌 현재 전략을
실시간으로 표시합니다. 모델이 작성한 HUD 문자열의 색상 태그와 줄바꿈은 서버에서 제거하며,
표시 내용은 실행 명령과 함께 전달된 관전용 텔레메트리이므로 게임 전략이나 판정에는 사용되지
않습니다.
HUD 항목과 모델의 전략·판단 요약은 한국어로 표시합니다. 실행 호환성을 위해 JSON 키와
Mindustry 블록·자원·유닛 식별자는 원래 영문 이름을 유지합니다.
HUD의 현재 전략은 최종 승리 조건이나 여러 단계의 미래 계획이 아니라, 현재 존재하는 시설·유닛·
가용 생산 슬롯으로 바로 시작할 수 있고 가까운 관측에서 결과를 확인할 수 있는 단기 목표입니다.
아직 없는 시설이나 유닛이 필요한 경우에는 그 선행 조건의 완성과 확인까지만 현재 목표로 삼고,
이후 단계는 새 상태를 받은 뒤 다시 판단합니다. 임의의 병력 수 할당이나 고정 빌드 순서는 두지
않습니다.

RTS 실행 직전에는 관측 상태에서 이미 생산 중인 공장·강화 중인 재구성기에 대한 명령,
아직 완성되지 않은 시설에 대한 생산 명령, 한 응답에서 같은 슬롯에 중복 제출된 후속 명령을
전략 변경 없이 제외합니다. 제외 내역은 `preflight_skips`로 로그와 다음 판단에 전달됩니다.
숫자 문자열·소수로 반환된 수량은 가장 가까운 정수로 바꾸고, 수량·예산·비율은 행동 계약의
허용 범위로 제한합니다. 좌표와 최종 실행 가능성은 변환 후에도 게임 서버가 다시 검증합니다.
생산된 전투 유닛은 LLM이 `command_units`로 직접 운용합니다. 유닛 종류 또는 상태에 표시된
개별 ID로 부대를 선택하고, 목표 건물 직접 공격, 좌표 공격 이동, 집결, 코어 후퇴, 정지를
결정할 수 있습니다. 이동과 사격은 Mindustry의 기본 지형 대응 명령 엔진이 수행합니다.
선택적 입력 생산망에는 `route_items_isolated`를 사용할 수 있습니다. LLM이 출발 건물, 도착
건물, 운반 자원, 운송 블록, 예산을 고르면 실행기는 출발·도착 자원 호환성을 확인하고 기존
벨트와 합류하지 않는 새 타일만으로 경로를 찾습니다. 또한 다른 자원 생산기나 기존 벨트가
새 경로로 유입될 수 있는 타일을 피하며, 기존 벨트를 덮어쓰거나 회전시키지 않습니다. 직선
거리보다 지나치게 긴 우회로밖에 없으면 아무것도 짓지 않고 측정된 경로 길이를 반환합니다.
생산 전략은 LLM이 유지하면서 벨트 혼입과 좌표 추측 실패를 줄이기 위한 명령입니다.
오염되거나 반복 실패한 선택적 소비처의 기존 입력망을 모델이 폐기하기로 결정한 경우에는
`clear_item_input_network`로 해당 소비처를 향하는 상류 벨트만 한도 내에서 제거하고, 다음
관측에서 새 출발점과 경로를 다시 선택할 수 있습니다. 실행기는 제거 대상을 입력망으로
한정하지만 어떤 생산시설을 재설계할지는 결정하지 않습니다.
일반 공유 경로도 선택적 입력 건물에 연결될 때 상류 생산물 집합을 검사하며, 대상이 받을 수
없는 자원이 함께 유입될 수 있으면 설치 전에 거부됩니다.
코어에 필요한 자원이 이미 쌓였는데 생산시설 입력망만 막힌 경우, LLM은
`command_core_unit`의 `supply` 모드로 자원과 목표 건물을 직접 선택할 수 있습니다. 코어
유닛은 실제 적재 용량과 이동 시간을 사용해 해당 건물로 반복 운반하므로 생산 교착을 풀면서
영구 물류망을 다시 설계할 시간을 확보합니다. 장기 공급망에는 코어 옆 `unloader`를 배치하고
`configure_item_filter`로 반출 자원을 지정할 수 있습니다. 두 기능 모두 모델이 사용 여부,
자원, 목표를 결정하며 실행기가 생산 우선순위를 고정하지 않습니다.
코어 유닛 임무는 비동기로 지속되며 새 임무가 이전 임무를 교체합니다. 상태의 경과 시간,
진행 단계, 적재량, 누적 배송량으로 완료 여부를 확인할 수 있어 같은 응답에서 채굴과 공급을
연속 지정해 앞선 작업을 즉시 덮어쓰는 실수를 구분할 수 있습니다.
관측 상태는 드릴의 실제 초당 생산량, 제작기의 초당 입력 요구량과 실제 출력량, 컨베이어의
표시 처리량, 입력망의 운송 블록 구성과 포화 좌표를 함께 제공합니다. LLM이 이 수치를 보고
필요하다고 판단하면 `upgrade_input_network`로 특정 선택적 입력 건물의 전체 상류 운송망을
선택한 상위 컨베이어로 교체할 수 있습니다. 실행기는 기존 좌표·방향·운반 중 아이템을
보존하고 비용과 교체 가능성을 원자적으로 검증하지만, 업그레이드 여부와 대상은 정하지 않습니다.

환경 변수로도 설정할 수 있습니다.

| 변수 | 기본값 | 의미 |
|---|---|---|
| `MINDUSTRY_API_URL` | `http://127.0.0.1:8765` | 게임 브리지 주소 |
| `MINDUSTRY_AGENT_TOKEN` | 빈 값 | 선택적 Bearer 토큰(서버와 에이전트에 동일 설정) |
| `MINDUSTRY_TEAM` | `sharded` | 단일 에이전트가 제어할 팀 |
| `MINDUSTRY_TEAM_TOKENS` | 빈 값 | PvP 팀별 토큰. 예: `sharded=...;crux=...` |
| `MINDUSTRY_AUTO_CORE_DEFENSE` | `true` | 에이전트 전용 코어 수비 기체 자동 생성·사격 |
| `LLM_BASE_URL` | `http://127.0.0.1:11434/v1` | OpenAI 호환 LLM 주소 |
| `LLM_MODEL` | `deepseek-v4.1-flash:cloud` | 기준 모델 |
| `LLM_MAX_TOKENS` | `2400` | 한 번의 전략 응답 출력 상한 |
| `LLM_REASONING_EFFORT` | `none` | 실시간성을 위해 DeepSeek의 장시간 내부 추론 비활성화 |
| `LLM_JSON_MODE` | `true` | JSON response format 사용 여부 |
| `DECISION_INTERVAL_SECONDS` | `0.5` | 최소 판단 간격; 모델의 `wait_seconds`가 더 크면 그 값을 사용 |
| `RUN_DIR` | `runs` | JSONL 로그 폴더 |

## 1차 평가 프로토콜

모델 비교 전에 아래 조건을 고정해야 합니다.

1. Mindustry v159.7, `Fork`, survival, 같은 게임 규칙과 시작 자원
2. 동일 행동 어댑터와 상태 스키마
3. 모델별 최소 5회 반복(가능하면 10회) 후 평균과 분산 보고
4. 추론 중 에피소드가 바뀐 턴은 성능 점수에서 제외하고 동기화 실패로 별도 집계

주 지표는 최대 생존 웨이브입니다. 보조 지표는 코어 생존/체력, 행동 성공률, 유효 건물 수, 코어 자원, 평균 LLM 지연, 입력·출력 토큰입니다. 단일 실행의 우연을 피하려면 평균뿐 아니라 표준편차와 최솟값도 함께 기록합니다.

## 현재 한계와 다음 순서

- v1은 건설 완료 시간을 생략하므로 실제 플레이어 조작과 동일하지 않습니다.
- 범용 임의 블록 설정과 회전 수정은 아직 없지만, 소유 건물 철거, 전력 노드 연결, 유닛 공장 생산 계획 선택은 지원합니다. 철거는 전략적 선택을 왜곡하지 않도록 자원 환급 없이 실행됩니다.
- 채굴 매크로는 코어 또는 LLM이 선택한 기존 건물을 목표로 삼고, 아이템·액체 경로 행동은 LLM이 선택한 두 건물 사이의 유효 경로만 계산합니다. 어떤 생산망과 방어선을 만들지는 어댑터가 결정하지 않습니다.
- 포탑 배치와 벽 배치는 LLM의 정확한 `place` 좌표를 사용합니다. `resupply_turrets` 보급 탄약은 실제 코어 자원에서 차감되며 자동 보급은 없습니다. 실제 이전량이 0이면 효과 없는 행동으로 기록됩니다.
- 서버는 플레이어가 없어도 맵 로테이션을 진행합니다. 각 반복 실험 전에 `host Fork survival`로 동일 맵을 다시 시작해야 합니다.

다음 구현은 이 기준선을 5~10회 완주해 로그를 확보한 뒤, 동일 API 위에 실패 메모리와 역할 분담을 가진 군집 에이전트를 올리는 것입니다.
